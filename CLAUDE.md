# Memoyce

Nama paket npm dan repositori: `memoyce` (dulu "Agent Memory Kit").

Library memori untuk AI agent, diinstall oleh aplikasi pemakai (misalnya aplikasi Sales Agent AI-Native). Penyimpanan di SurrealDB. **AI milik aplikasi pemakai yang memanggil tool memori ini**; library tidak memanggil LLM.

## Stack

- TypeScript (ESM), kode library di `src/` (`src/index.ts` = API publik, `src/core/` = internal). Target runtime: **Bun dan Node**. Kode di `src/` tidak boleh memakai API Bun (`Bun.*`, `bun:*`). Bun hanya untuk pengembangan: `bun test`, `bun install`.
- Penyimpanan: SurrealDB (dokumen + graf + full-text + vektor dalam satu basis data) lewat paket `surrealdb`. Engine dipilih pemakai: `rocksdb://`, `surrealkv://`, `mem://` (embedded lewat `@surrealdb/node`), atau `ws://`/`http://` (server remote). Semua memakai SurrealQL yang sama; tidak ada lapisan abstraksi database lain.
- Perintah: `bun run typecheck` (tsc), `bun run lint` / `bun run format` (Biome), `bun test`, `bun run test:coverage`. Jalankan typecheck, lint, dan test:coverage sebelum menyelesaikan pekerjaan.
- Tambah dependensi hanya bila perlu.
- **Paket npm (`memoyce`, ESM, MIT).** Impor relatif di `src/` memakai ekstensi `.ts` (`from "./core/x.ts"`); `tsconfig.build.json` dengan `rewriteRelativeImportExtensions` mengubahnya menjadi `.js` pada keluaran, dan `scripts/build.mjs` merapikan impor `.ts` yang tersisa di `.d.ts` (agar valid untuk pemakai `node16/nodenext`). `bun run build` -> `dist/`. `files` hanya `dist`, README, LICENSE. Dependensi: `zod` (dependencies), `surrealdb` (peerDependencies, karena instance `Surreal` pemakai bisa diberikan lewat `storage: { db }`), `@surrealdb/node` + `@surrealdb/node-native` (optionalDependencies, dimuat dinamis hanya untuk `mem://`/`rocksdb://`/`surrealkv://`; tanpa keduanya, `MemoryError("storage")` dengan pesan yang menjelaskan). Jangan mengimpor `@surrealdb/node` secara statis.
- **Rilis otomatis (GitHub Actions, meniru paket njin):** `.github/workflows/ci.yml` (setiap push/PR ke main: Biome, typecheck, test:coverage; plus build dan smoke test di Node 20 dan 22), `codeql.yml`, dan `release.yml`. Cara merilis: naikkan `version` di `package.json`, commit dan push, lalu buat GitHub Release dengan tag `vX.Y.Z` yang SAMA dengan versi itu. Saat Release dipublikasikan, `release.yml` memverifikasi tag = versi, menjalankan lint/typecheck/test/build/smoke, lalu `npm publish --provenance` (butuh repo publik dan secret `NPM_TOKEN` di repositori). Pra-rilis (`0.2.0-beta.1`) terbit dengan dist-tag `beta`, bukan `latest`. Langkah manual yang setara:
- **Rilis manual:** `bun run typecheck && bun run lint && bun run test:coverage`, `bun run build && bun run smoke` (Node murni), lalu uji tarball: `npm pack`, pasang ke folder kosong, jalankan `node scripts/smoke.mjs memoyce`, dan kompilasi file TypeScript pemakai dengan `module/moduleResolution: nodenext` dan `skipLibCheck: false` (sudah pernah bersih). `prepublishOnly` menjalankan typecheck, lint, test, dan smoke. Versi `0.x`: antarmuka masih bisa berubah; semver ketat sejak 1.0.

## Prinsip Desain

Lima persyaratan ini adalah kontrak sistem. Setiap perubahan harus menjaganya.
1. **Fakta terstruktur, bukan sekadar potongan chat.** Memori disimpan sebagai entitas, atribut, dan nilai. Potongan teks mentah hanya menjadi sumber, bukan unit memori.
2. **Sadar waktu.** Fakta lama ditutup (diberi waktu berakhir), tidak pernah dihapus. Sistem harus bisa menjawab "benar pada tanggal X". Pembaruan nilai = tutup fakta lama + buat fakta baru, dalam satu transaksi.
3. **Punya sumber (provenance).** Setiap fakta menunjuk ke teks asalnya. Fakta tanpa sumber tidak boleh disimpan. Setiap fakta membawa `quote` dari AI pemanggil, dan `remember` memverifikasi bahwa kutipan itu benar-benar ada di teks sumber (tanpa beda huruf/spasi, minimal 3 karakter) sebelum menulis apa pun.
4. **Pencarian hibrida.** Kombinasi kata kunci (full-text), makna (vektor), dan relasi (traversal graf). Hasil dari ketiganya digabung dan diperingkat. Tanpa embedder, jalur vektor dilewati dan sisanya tetap jalan.
5. **Berani menjawab "tidak tahu".** Jika data tidak ada atau skor retrieval di bawah ambang, hasilnya harus eksplisit `found: false` dengan pesan jangan menebak. Library tidak memanggil LLM untuk mengisi celah.

## Kontrak Library

- **Tanpa state global dan tanpa `process.env`.** Semua konfigurasi masuk lewat opsi `createMemory(options)`; semua state ada di instance (`Ctx` di `src/core/context.ts`). Fungsi internal menerima `ctx` sebagai argumen pertama. Aplikasi boleh membuat banyak instance. (Aturan lama "state module-level, jangan DI" sudah dicabut.)
- **Tanpa klien LLM.** AI pemanggil mengekstrak fakta dan mengirimnya terstruktur lewat tool. Satu-satunya yang pluggable adalah `embedder` (opsional): `{ model, dimension, maxBatch?, embed(texts, { kind: "document" | "query" }) }`. Model dan dimensi dicatat di `meta:embedding`; embedder yang berbeda dari yang tercatat (atau data lama tanpa vektor) ditolak dengan `embedder_mismatch`, kecuali `onEmbedderChange: "reindex"` atau `memory.reindex()`. Kegagalan embedder dilempar sebagai `MemoryError("embedder")` SEBELUM penulisan, jadi tidak ada data setengah tertulis.
- **Tool netral, tanpa adapter.** Definisi tool = `{ name, description, inputSchema (JSON Schema dari zod), execute }`. Aplikasi menempelkannya ke SDK AI-nya sendiri. `execute` memvalidasi input dan mengembalikan kegagalan yang bisa diperbaiki sebagai **data** (kode + saran), tidak melempar.
- **Scope = kepemilikan, buram bagi library.** Setiap panggilan tulis menerima satu `scope` (string bebas, misalnya `org:42/lead:7`); baca menerima satu atau beberapa scope. Library tidak tahu arti scope, tetapi **menegakkannya di lapisan query** (retrieval hibrida terjadi di dalam library, jadi filter tidak boleh diserahkan ke aplikasi). Entitas, sumber, dan fakta terikat scope; mereferensikan record scope lain ditolak, baik di kode (`scope_mismatch`) maupun di skema (ASSERT).
- **Netral bahasa: library tidak membawa daftar kata bahasa apa pun.** Kata fungsi ("apa", "what", "les") dan gelar/badan usaha ("pt", "mr", "ibu") adalah opsi aplikasi: `retrieval.stopwords` dan `retrieval.titles` (bawaan kosong). Tool memintanya dari AI pemanggil (yang multibahasa) dengan menyuruh `query` berupa kata kunci isi tanpa kata tanya, dalam bahasa data, sehingga jalur tool tidak butuh daftar sama sekali. Terukur (Gemini, 0,76/0,5): tanpa daftar, AI menulis query -> 94%; daftar Indonesia diisi aplikasi, kalimat mentah -> 92%; tanpa daftar, kalimat mentah -> 74% (jalur kata kunci batal karena "apa/berapa" dianggap istilah tak dikenal, jatuh ke vektor; arah gagal tetap aman, ke "tidak tahu"). Pemanggil langsung `memory.recall`/`context` dengan kalimat sebaiknya mengisi `stopwords` (sumber daftar, mis. paket `stopwords-iso`, milik aplikasi, bukan dependensi library). Pemecah kata memakai pemisah Unicode (huruf/angka) dan indeks BM25 SurrealDB; untuk bahasa tanpa spasi (Mandarin, Jepang, Thai) jalur kata kunci dan nama sebagian tidak andal, hanya vektor yang bekerja.
- **Kosakata atribut dikonfigurasi aplikasi** (`attributes`): `key`, `description`, `type` (`string|number|boolean|date|entity|json`), `cardinality` (`single|multi`), `aliases`. Library tidak membawa kosakata domain. Mode `vocabulary: "strict"` (default) menolak atribut tak dikenal dengan saran; `"open"` menerimanya sebagai `json` bernilai tunggal. Tabel `attribute` di DB hanya cermin konfigurasi (atribut yang dihapus dari konfigurasi ditandai `active = false`, tidak dihapus).
- **Penyimpanan** lewat `storage: { url }` (library membuka dan menutup koneksi) atau `storage: { db }` (instance `Surreal` milik aplikasi; library memakai session sendiri dan tidak menutup koneksinya). Path embedded dinormalisasi menjadi relatif terhadap cwd karena engine memotong drive Windows (`normalizeUrl`).
- **API publik** hanya yang diekspor `src/index.ts`: `createMemory`, tipe, `MemoryError`. Semver berlaku sejak rilis pertama. `assertFact`, `RecordId`, dan fungsi `src/core` lain bersifat internal.
- **Migrasi skema** otomatis saat `createMemory` (`migrate: "auto" | "check" | "off"`). Daftar `migrations` di `src/core/migrations.ts` **hanya boleh ditambah di akhir**; migrasi yang sudah dirilis tidak boleh diubah. Tiap migrasi idempoten (`DEFINE ... IF NOT EXISTS`), bersifat aditif bila mungkin, dan berjalan dalam transaksi bersama pembaruan `meta:schema`. Database yang versinya lebih baru dari library ditolak.

## Model Data (skema versi 5)

- `source`: `scope`, `content`, `received_at`, `meta`. Teks asal.
- `entity`: `scope`, `name`, `kind`, `aliases`, `embedding` (opsional), `keys` (nama + alias ter-normalisasi, dihitung DB lewat `VALUE`; harus identik dengan `entityKey()` di `entities.ts`: trim + huruf kecil). Index `(scope, keys)`. `words` (migrasi v5): kata-kata nama + alias (huruf kecil, dipisah pada selain huruf/angka), juga dihitung DB lewat `VALUE`; index `(scope, words)` dipakai pencocokan nama sebagian.
- `attribute`: cermin kosakata (id = key).
- `fact`: `scope`, `entity`, `attribute`, `value` (literal, atau referensi `entity` untuk relasi), `valid_from`, `valid_to` (`NONE` = masih berlaku), `source` wajib, `quote` (opsional di skema, selalu diisi oleh `remember`), `text` (kalimat fakta untuk full-text dan embedding, mis. "PT Maju · anggaran: 75000000 — Budget naik jadi 75 juta"). **Satu struktur untuk atribut dan relasi**; tidak ada tabel edge `RELATE`. Edge ditambahkan hanya bila pengukuran menunjukkan traversal membutuhkannya.
- `meta`: `meta:schema` (versi skema) dan `meta:embedding` (model + dimensi vektor).
- Partisi vektor `fvec_<hash(scope)>` (fakta) dan `evec_<hash(scope)>` (entitas): satu tabel + satu index HNSW per scope, dibuat lazy dan idempoten (`vectors.ts`). Baris vektor memakai id yang sama dengan fakta/entitasnya; `fvec` membawa `valid_from`/`valid_to` yang disinkronkan saat fakta ditutup (dalam transaksi yang sama). Ini **data turunan**: boleh dihapus dan dibangun ulang (`reindex`), tidak melanggar aturan "jangan hapus fakta".
- Index lain: full-text BM25 pada `fact.text` (analyzer `blank, class, punct` + `ascii, lowercase`, tanpa stemmer karena multibahasa), `fact(scope, value)` untuk pencarian balik relasi, `entity(scope, keys)`.
- Query "pada tanggal X": `valid_from <= X AND (valid_to = NONE OR valid_to > X)`. Index selalu berawalan `scope`.
- `single`: nilai baru menutup nilai lama. `multi`: nilai ditambah, nilai lain tidak disentuh; penutupan lewat `retractFact`.

## remember

`memory.remember({ scope, source: { content, received_at?, meta? }, facts: [{ entity, attribute, value, quote, valid_from? }] })`. Input berupa JSON murni (tanggal ISO string) supaya skemanya (`rememberSchema`) bisa menjadi JSON Schema tool.
- **Dua tahap.** Tahap 1 hanya membaca: skema input, atribut (strict/open), tipe nilai, kutipan, dan resolusi entitas untuk semua fakta. Satu saja yang tidak valid = **tidak ada yang ditulis**, dan semua galat dikembalikan sekaligus (`{ ok: false, stage: "validation", errors }`, tiap galat punya `index`, `code`, `details`). Tahap 2 menulis sumber, entitas baru, lalu fakta menurut urutan waktu berlaku (urutan input tidak memicu `stale_time`). Kegagalan saat menulis (mis. `stale_time` karena menyisipkan fakta lebih lama dari yang berlaku) dilaporkan per fakta (`stage: "write"`); yang berhasil tetap tersimpan.
- **Rujukan entitas:** string (nama), `{ name, kind? }`, atau `{ id: "entity:..." }`. Resolusi: nama/alias persis (tanpa beda huruf) dalam scope. Satu cocok = dipakai (kind hanya petunjuk); lebih dari satu = `kind` menyaring, sisanya `ambiguous_entity` dengan daftar kandidat; tidak ada = dibuat (kind default `unknown`). Entitas yang sama disebut berkali-kali dalam satu panggilan = satu entitas. Untuk atribut bertipe `entity`, nilai memakai bentuk rujukan yang sama.
- `valid_from` default = `received_at` sumber (waktu fakta disampaikan), bukan waktu pemrosesan.
- Id di antarmuka berbentuk teks `tabel:id` (`idToString`/`parseId` di `ids.ts`). Id dibuat tanpa tanda minus (`newId`).
- Belum ada pencegahan duplikat entitas pada panggilan `remember` yang bersamaan (dua proses membuat entitas bernama sama sekaligus); tidak ada unique index karena nama sama boleh dipakai entitas berbeda kind.

## Vektor dan recall

**Mengapa vektor per scope.** Terukur di SurrealDB 3.x: KNN dengan filter scope berbiaya linier terhadap ukuran scope (0,3-2 detik pada 90 ribu baris, dan filter `valid_to` di dalam KNN lebih buruk), sedangkan KNN tanpa filter cepat. Jadi KNN selalu dijalankan tanpa filter di dalam partisi scope, dan validitas waktu disaring sesudahnya (ambil kandidat lebih banyak, perluas bila perlu, batas 2000). Jangan menambah filter ke operator `<|k,ef|>`.

`memory.recall({ scope (string | string[]), query, as_of?, limit?, min_similarity?, min_keyword_coverage? })` menggabungkan tiga kanal:
- **Vektor:** ANN pada `fvec` (query di-embed dengan `kind: "query"`).
- **Kata kunci:** BM25 dengan semantik OR (`@0,OR@`) pada `fact.text`. Skor BM25 hanya dipakai untuk peringkat: pada korpus kecil bisa 0 walau kata cocok persis. Bukti kata kunci = **cakupan istilah query**: porsi istilah bermakna (tanpa kata tanya/penghubung dari `contentTerms`, **dan tanpa istilah yang merupakan nama entitas yang disebut di query**) yang ada di teks fakta. Nama entitas dikecualikan karena muncul di teks semua faktanya (subjek maupun nilai) sehingga tidak membedakan fakta yang menjawab; tanpa ini "alamat kantor PT Maju" menganggap fakta anggaran PT Maju relevan. Kandidat dengan cakupan 0 tidak mendapat peringkat di kanal kata kunci (RRF hanya melihat peringkat, jadi tanpa ini fakta yang hanya cocok lewat nama entitas bisa menyaingi yang menjawab).
- **Graf:** entitas yang disebut (n-gram query dicocokkan ke `entity.keys`, dan kemiripan makna ke `evec`), lalu fakta langsung entitas itu dan fakta berelasi satu lompatan (nilai yang menunjuk ke entitas itu, atau milik entitas yang ditunjuk faktanya). Kandidat graf yang lolos dari ANN dinilai kemiripannya lewat lookup id langsung.

**Kecocokan terpanjang menang** (`mentions.ts`): entitas yang semua penyebutannya di query hanyalah bagian dari nama entitas lain yang lebih panjang dalam scope yang sama ("PT Maju" dalam "PT Maju Jaya") dianggap salah sasaran. Ia tidak ditautkan (juga tidak lewat kemiripan `evec`), dan faktanya (sebagai subjek atau nilai) dibuang dari semua kanal sebelum fusi. Bila nama pendek juga disebut di tempat lain pada query, ia tetap dianggap disebut.

**Nama sebagian** (`mentions.ts`, `partialEntities`): rangkaian kata query yang sama dengan potongan berurutan nama/alias entitas tanpa gelar ('Budi' -> Budi Santoso, 'Ibu Sari' -> Sari Wulandari, 'Nusantara Logistik' -> PT Nusantara Logistik) menautkan entitas. Gelar dan badan usaha dilewati dan tidak dihitung bukti isi (daftarnya dari aplikasi, `retrieval.titles`); kata tanya dan kata atribut (key, deskripsi, alias) tidak boleh memicu tautan; kata di bawah 3 huruf atau angka tidak dihitung; kata yang sudah dijelaskan penyebutan persis dilewati. Penyebutan lebih panjang menang. Bila beberapa entitas cocok sama baiknya (dua 'Budi'), SEMUANYA ditautkan dan nama masing-masing muncul di hasil, tidak ditebak satu. Ini deterministik (tanpa embedding); kemiripan makna nama (`evec`) hanya cadangan bila tak ada nama yang cocok.

**Jangkar entitas.** Entitas yang disebut persis (nama/alias) menjadi jangkar: bila ada, hanya fakta entitas itu dan relasi satu lompatannya yang boleh menjawab; fakta entitas lain yang kebetulan memuat istilah sama ("anggaran") dibuang. Entitas hanya ditautkan lewat kemiripan makna (`evec`) bila TIDAK ada yang disebut persis, dengan ambang `ENTITY_MIN_SIMILARITY` (0,75) selain `minSimilarity`: kemiripan dasar model embedding pada teks pendek tinggi, jadi ambang umum menautkan 5 entitas acak pada setiap query. Istilah yang menamai entitas dikecualikan dari bukti kata kunci hanya untuk entitas yang disebut persis.

**Istilah tak dikenal membatalkan bukti kata kunci.** Bila ada istilah isi query yang tidak muncul di teks fakta mana pun dalam scope ("sentosa", "cuaca"), cakupan kata kunci tidak dihitung sebagai bukti (tidak ada fakta yang bisa memenuhinya; kecocokan sebagian pada istilah lain menyesatkan). Bukti lewat makna (kosinus >= `minSimilarity`) tetap berlaku. Pada relasi dua lompatan, istilah yang dijelaskan fakta penghubung ("pengambil keputusan" pada "jabatan pengambil keputusan PT Maju") dihitung terpenuhi (`Candidate.via`). Kata fungsi ("apa", "what", "ada") dikecualikan lewat `retrieval.stopwords` dari aplikasi.

**Hasil kalibrasi (evals/, Gemini `gemini-embedding-001@768`):** `minSimilarity` 0,76 dan `minKeywordCoverage` 0,5 memberi akurasi 90% (dari 65%), pertanyaan tak terjawab yang dijawab menebak 5% (dari 95%), kebocoran 0%. Ambang bergantung model: jalankan `bun run eval --sweep` untuk setiap embedder. Menaikkan ambang menurunkan menebak tetapi juga parafrasa yang benar (parafrasa lemah di 0,76: 4 dari 7). Kegagalan yang diketahui: pertanyaan dua lompatan yang separuh terjawab ("anggaran perusahaan tempat Rina bekerja" mengembalikan fakta tempat kerja Rina) dan resolusi entitas longgar ("perusahaan Pak Hendra").

Fusi RRF (bobot vektor 1, kata kunci 1, graf 0,5). **Skor RRF berbasis peringkat sehingga selalu menghasilkan sesuatu**; yang menentukan "tahu atau tidak" adalah ambang absolut: kemiripan kosinus >= `minSimilarity` ATAU cakupan istilah >= `minKeywordCoverage`. Fakta yang hanya terhubung lewat entitas tanpa bukti isi **tidak** dikembalikan. Hasil tanpa bukti = `{ found: false, items: [], linked_entities, message: "... Jangan menebak." }`.

**Ambang bawaan (0,5 / 0,5) belum dikalibrasi.** Kemiripan bergantung pada model embedding; kalibrasi dengan set evaluasi berlabel (pertanyaan yang bisa dan tidak bisa dijawab) pada model sungguhan sebelum dipakai produksi. Tes memakai embedder palsu (bag-of-words) yang hanya menguji mekanisme, bukan mutu semantik.

## Konteks siap suntik (`memory.context`)

`memory.context({ scope, query?, as_of?, limit?, quotes? })` mengembalikan `{ found, text, items, entities }`; `text` adalah blok ringkas siap ditaruh di prompt (briefing.ts).
- **Tanpa `query`: briefing** fakta berlaku terbaru (urut `valid_from` menurun, dikelompokkan per entitas, nilai lama yang sudah diganti tidak ikut). Ini yang memungkinkan AI berinisiatif melanjutkan konteks di awal sesi atau panggilan stateless, tanpa menunggu pertanyaan atau memanggil tool. Memakai index `fact(scope, valid_from)` (migrasi v4) agar tidak memindai seluruh scope; query dijalankan per scope lalu digabung.
- **Dengan `query`:** fakta relevan (memakai `recall`) dalam bentuk teks.
- Selalu tegas: memori kosong atau tidak punya jawaban menghasilkan kalimat eksplisit ("belum ada informasi" / "Jangan menebak"), bukan teks kosong.
- Label baris memakai bagian depan `description` atribut (sebelum " ("), jadi jaga deskripsi atribut tetap ringkas di depan.
- Library tidak memutuskan apa yang diingat atau kapan briefing diminta; itu urusan aplikasi.

## Tool untuk AI

`memory.tools({ scope, readScopes?, sourceMeta?, readOnly? })` mengembalikan definisi netral `{ name, description, inputSchema (JSON Schema draft-7), execute }`: `memory_remember`, `memory_recall`, `memory_list_attributes` (`readOnly` membuang yang pertama). Input dan hasil adalah JSON murni.
- **Keamanan: yang menentukan kepemilikan adalah APLIKASI, bukan AI.** `scope` (tulis) dan `readScopes` (baca, default `[scope]`) diikat saat tool dibuat. Skema tool tidak memuat `scope`, `source.meta`, maupun ambang bukti; nilai kiriman AI untuk field itu **diabaikan** (`pick` hanya mengambil field yang diizinkan, lalu scope/meta ditimpa). Jangan pernah menambahkan field kepemilikan atau ambang ke skema tool.
- `memory_recall` juga memuat kosakata atribut dan aturan menulis `query`: AI mempertahankan semua entitas dan kata kunci, mengganti kata dengan kata dari DESKRIPSI atribut hanya bila maknanya sama persis, tidak memakai nama teknis atribut (tidak ada di teks fakta), dan TIDAK mengganti hal yang tak ada di kosakata dengan atribut yang berdekatan. Terukur (`bun run eval --rewrite`): tanpa vektor, terjawab 38 -> 44 dari 53 dengan tebakan tetap 5%; dengan vektor (0,76/0,5) 46 -> 48 dari 53 (deskripsi lama vs baru), sama dengan pertanyaan asli yang sudah bersih, tebakan 5%. Jadi manfaatnya terutama ketahanan bila vektor mati atau pengguna menulis tidak rapi, bukan lompatan di atas pertanyaan bersih. Versi awal yang menyuruh "pakai istilah dari daftar" tanpa batasan membuat AI mengubah pertanyaan jadi pertanyaan lain ("kompetitor" -> "preferensi") dan tebakan naik ke 16%; jangan melonggarkan kalimat larangannya tanpa mengukur ulang.
- `description` dibangun dari kosakata atribut terdaftar (key, tipe, kardinalitas, alias) dan memuat instruksi: wajib `quote`, perbaiki bila `ok: false`, dan `found: false` berarti jangan menebak.
- Kesalahan yang bisa diperbaiki AI (atribut tak dikenal, kutipan, entitas ambigu, input rusak) dikembalikan sebagai data (`ok: false` + `errors`), tidak dilempar. Galat infrastruktur (embedder, DB) tetap dilempar sebagai `MemoryError`; aplikasi yang memutuskan cara menampilkannya ke AI.
- Tanggal di skema divalidasi dengan `refine` (`schemas.ts`), bukan regex zod, karena pola regex ikut ke JSON Schema dan memboroskan token LLM. Beri `.describe()` pada field baru yang dilihat AI.
- Tidak ada adapter per SDK; aplikasi memetakan nama field sendiri (contoh di README).

## Aplikasi uji (examples/cli)

Chat terminal dengan Gemini (`@google/genai`, devDependency) + embedding OpenAI atau Gemini, untuk menguji dengan LLM sungguhan; lihat `examples/cli/README.md`. Aturan: **bukan bagian library** (tidak diimpor dari `src/`, tidak ikut paket, dikecualikan dari coverage); membaca environment variable boleh di sini saja. Logika murni (`agent.ts` loop tool dan pemotongan riwayat per giliran, `embedders.ts`) dites tanpa jaringan di `tests/units/example-cli.test.ts` dengan model palsu. Tool memakai `parametersJsonSchema` Gemini, jadi skema tool kita dipakai apa adanya. Bagian model yang dikembalikan Gemini disimpan utuh di riwayat (model generasi baru butuh thought signature).

## Evaluasi retrieval (evals/)

Set evaluasi berlabel untuk mengukur akurasi `recall` dan mengkalibrasi ambang; lihat `evals/README.md`. `bun run eval` (embedding sungguhan; `--failures`, `--sweep`). **Bukan bagian library** (dikecualikan dari paket; `run.ts` dari coverage). Dataset/penilai/harness dites di `tests/units/eval.test.ts` dengan embedder palsu. Fakta sudah diekstrak tangan, jadi yang diukur retrieval, bukan ekstraksi LLM. Setiap perubahan pada `recall`/resolusi entitas/ambang dijalankan ulang terhadap set ini; kegagalan nyata dari aplikasi ditambahkan sebagai pertanyaan baru.

## Benchmark skala (bench/)

`bun bench/scale.ts --mode scopes|big [--engine rocksdb]` (banyak scope kecil, atau satu scope besar) dan `bun bench/profile.ts` (waktu tiap kueri recall pada satu scope besar). **Bukan bagian library, tanpa API eksternal**: embedder tiruan 768 dimensi hanya untuk biaya penyimpanan/indeks/query, bukan mutu semantik. Hasil pada `mem://` dan RocksDB (komit 7de6e61):
- **Vektor per scope aman, dan jumlah scope hampir tidak berbiaya.** ANN fakta datar (~8 ms) dari 4 ribu sampai 12 ribu fakta. Biaya TETAP per scope (partisi vektor kosong, RocksDB): ~8 KB disk, ~33-38 ms untuk membuat (konstan sampai 3000 scope = 6000 tabel + 6000 indeks HNSW), tanpa tambahan memori, buka ulang database 100 ms, `ensure` scope yang sudah ada 7-12 ms setelah buka ulang. 1000 scope x 20 fakta: waktu tulis per scope konstan, recall 18-33 ms, jawaban benar 40/40. Koreksi: angka memori "1,4 MB per scope" pada `mem://` adalah biaya per FAKTA (~60-70 KB per fakta, sama dengan satu scope besar), bukan per scope. Scope kecil justru lebih cepat daripada scope besar karena kueri yang linear hanya memindai satu scope.
- **Biaya sebenarnya ada pada jumlah vektor.** RocksDB, 768 dimensi, HNSW M=12 EFC=150: ~27 KB disk per vektor (±9x ukuran mentah 3 KB), tidak mengecil setelah ditutup. Total ~50 KB disk per fakta dengan vektor (dua tabel vektor: fakta dan entitas), ~10 KB tanpa vektor. Perkiraan: 100 ribu fakta = ~5 GB; **Dimensi embedding** (Gemini `gemini-embedding-001` lewat `outputDimensionality`, `EMBEDDING_DIMENSION=... bun run eval --sweep`; 200 scope x 20 fakta di RocksDB, disk setelah ditutup): 768 -> 204 MB, 384 -> 151 MB, 256 -> 116 MB, 128 -> 92 MB (tanpa vektor: 39 MB). Penghematan nyata tetapi tidak proporsional, karena biaya graf HNSW dan indeks lain tetap. Mutu pada set evaluasi (tebakan <= 5%, kebocoran 0%, ambang terbaik masing-masing): 768 d @0,76 -> akurasi 92%, 48/53 terjawab; 384 d @0,78 -> 89%, 46/53; 256 d @0,82 -> 88%, 45/53; 128 d @0,88 -> 88%, 45/53. **Ambang bergeser tajam menurut dimensi** (0,76 -> 0,88): kalibrasi ulang untuk setiap dimensi. Set evaluasi kecil (166 fakta): selisih 2-3 jawaban masih dalam derau, dan dimensi kecil kemungkinan lebih cepat memburuk pada scope besar dengan banyak entitas mirip; ukur ulang dengan data nyata sebelum memilih. Belum dicoba: M/EFC lebih kecil, melewatkan vektor entitas, vektor hanya untuk scope besar (brute force untuk scope kecil).
- **Recall dan remember linear terhadap ukuran scope** (1,2 detik per recall @20 ribu fakta; pengisian melambat dari 40 ke 200 ms per lead). Penyebab (terbukti lewat `EXPLAIN`): indeks hanya dipakai pada awalan scope, sisanya disaring satu per satu: `keys CONTAINSANY` / `words CONTAINSANY` pada entitas (indeks `(scope, keys)` tidak mengindeks elemen array), `entity IN`/`value IN`/`OR` pada fakta, `ORDER BY valid_from` (planner memilih `fact_scope_recent` lalu menyaring entitas), `count()` untuk istilah tak dikenal dan BM25 OR pada kata umum. Yang memakai indeks dengan benar: `entity = $x` (fact_current), `value = $x` (fact_scope_value), indeks `keys.*` pada entitas, `text @@ ... LIMIT 1`.
- **Bug (SUDAH DIPERBAIKI): nama entitas lebih dari 4 kata tidak pernah cocok persis** (n-gram maksimal 4). Pada 5 ribu fakta dengan nama 5 kata, jawaban benar jatuh 17/30 -> 4/30. Sekarang n-gram sampai 8 kata (batas 100 potongan per ukuran, bukan total, supaya potongan terpanjang tidak terbuang lebih dulu), dan nama 5 kata kembali 30/30. Nama lebih dari 8 kata masih tidak cocok persis (hanya sebagian).
- RocksDB: ~55 KB disk per fakta (554 MB untuk 10 ribu fakta, diukur sebelum ditutup), buka ulang 154 ms. Belum diselidiki.
- Belum dicapai: "ratusan ribu fakta per scope". Perbaikan yang direncanakan: indeks `keys.*`/`words.*` (migrasi v6), kueri per entitas dengan `=` lalu urut di TypeScript, cek keberadaan istilah dengan `LIMIT 1`, istilah langka untuk kandidat BM25.

## Aturan Kerja

- Jangan pernah `DELETE` fakta untuk menangani perubahan; tutup dengan `valid_to`. Penghapusan nyata hanya lewat `forget` untuk permintaan privasi eksplisit (satu-satunya jalur `DELETE`, khusus aplikasi, bukan tool AI; belum dibuat).
- Semua input dari luar (opsi, argumen tool) divalidasi zod sebelum menyentuh DB.
- Kegagalan yang bisa diperbaiki pemanggil memakai `MemoryError` dengan `code` stabil dan `details` terstruktur. Di dalam transaksi SurrealQL, `THROW "kode:detail"` lalu dipetakan kembali di TypeScript.
- Kunci API dan kredensial tidak ada di library; mereka milik aplikasi.
- Komentar dan pesan galat berbahasa Indonesia, mengikuti kode yang ada.

## Pengujian

- `bun test`, root `tests/`: `tests/units/` (satu modul; DB nyata `mem://` boleh dipakai karena logika ada di SurrealQL), `tests/features/` (alur ujung ke ujung; hanya batas eksternal yang dipalsukan), `tests/support/` (helper `openTestContext`).
- Coverage line dan function minimal 95% (`bunfig.toml`, gagal otomatis). Skenario fitur diturunkan dari 5 prinsip desain, bukan dari angka coverage. Modul baru dibuat bersama tes unit dan skenario fitur-nya.
- Builder SDK (`db.create(...)`, `db.query(...)`) bersifat thenable, bukan Promise: bungkus dengan fungsi `async` sebelum memakai `expect(...).rejects`.
- `rmSync` Bun di Windows gagal diam-diam untuk path relatif `./...`; pakai `path.resolve` untuk path yang dihapus.
- Test untuk penyimpanan embedded sungguhan (`rocksdb://`) ditaruh di `data/` (di-ignore git) dan dibersihkan sendiri.
